# YiYi OpenDataBox Workspace-Bench Bad Case 分析报告

## 1. 背景

本报告基于清洗后的 100 个正常完成任务进行分析。清洗规则如下：

- 原始正常任务使用 `YiYiOpenDataBox--local-yiyi--Ten3PhaseFix`
- 原始失败后重跑任务使用 `YiYiOpenDataBox--local-yiyi--Ten3PhaseFixRerunFailed2`
- 原始受余额污染的 5 个任务使用 `YiYiOpenDataBox--local-yiyi--Ten3PhaseFixRerunBalance5b`
- 原始 judge 中断任务以补评后的 judge 文件为准

清洗后的合并视图目录为：

```text
Workspace-Bench/evaluation/output/YiYiOpenDataBox--local-yiyi--Ten3PhaseFixClean100
```

该目录使用 symlink 指向各 source run 的 task 目录，并额外生成：

- `clean_manifest.json`
- `clean_summary.json`
- `agent_runner_report.json`

## 2. 总体结果

清洗后的 100 个任务均有 agent 输出与 judge 结果：

```text
任务数: 100
通过 rubrics: 1004 / 1856
通过率: 54.09%
API 错误任务数: 0
Judge 执行错误任务数: 0
```

本报告已去除余额不足、judge SIGTERM 等异常样本口径，只分析正常运行后仍然低分的真实 bad case。

## 4. 主要失败模式

### 4.1 目录与路径结构错误

这类任务通常已经生成了部分文件，但没有按 rubric 要求创建子目录或保存到指定位置。

| Task ID | 现象 | 判断 |
| --- | --- | --- |
| 7 | 要求创建 `project_kickoff_archive/` 并放入 3 个指定文件；实际输出是扁平目录，并包含大量无关文件 | 未遵守目录结构与文件筛选要求 |
| 146 | 要求创建 `sops/` 目录并放置 19 个 SOP；实际没有 `sops/` 目录，`sops_output.md` 位于输出根目录 | 未执行目录创建与文件组织 |
| 372 | 要求在 `temp_pending/` 下生成重命名文件；实际没有该目录，只生成 `Renaming_Log.txt` | 只生成日志，未完成文件操作 |
| 23 | 要求将 `Inventory_Optimization_Report.txt` 保存到 `/budget-management/inventory-optimization/`；实际放在输出根目录 | 输出路径错误 |

根因判断：YiYi 当前对“必须保存到指定路径/子目录”的约束执行不稳定，容易把最终文件统一写到 `model_output` 根目录。

### 4.2 源文件定位或任务主题错误

这类任务的输出内容看似完整，但对应了错误文件或错误主题。

| Task ID | 现象 | 判断 |
| --- | --- | --- |
| 124 | 要求抽取 `CL-BENCH` 论文摘要；实际输出是 Product Hunt / Discovery Gap 相关论文 | 源文件定位错误 |
| 120 | 要求总结 AI Agent 架构、CL-Bench、开发环境三类截图；实际分成商业数据分析和 LLM 技术分享会 | 截图主题识别错误 |
| 388 | 要求生成 2025 年 NovaMind Q1/Q2 策略 PPT；实际 PPT 使用 2026 年、上海 W 酒店等错误背景 | 输入集合或上下文混淆 |
| 288 | 要求服饰电商产品分析；实际输出偏城市、财务等维度，缺 TOP10 产品表 | 目标数据源定位偏移 |

根因判断：Phase 1/Phase 2 的检索与筛选阶段容易被相似文件或全局 workspace 噪声干扰，未能锁定 rubric 对应的精确源文件。

### 4.3 文件存在但格式或 Schema 不符合

这类 case 的目标文件存在，但和 benchmark 要求的精确结构不一致，例如 sheet 名、列名、页数、文件扩展名或字段数量错误。

| Task ID | 现象 | 判断 |
| --- | --- | --- |
| 258 | 要求 3 个 worksheet：`Employee Settlement Details`、`Job Summary Statistics`、`Exception Data Description`；实际有 Cover、Jan Salary、Feb Salary 等多个不匹配 sheet | Excel schema 错误 |
| 207 | `Talent_Evaluation.xlsx` 存在，但 sheet 名、列名、候选人分数均不符合要求 | 表结构与计算均不匹配 |
| 291 | 要求 `.xls` 和 5 个 worksheet；实际为 `.xlsx` 且有 6 个 worksheet，关键目标数值也错误 | 文件格式、sheet 数、数值均错误 |
| 381 | PPT 存在，但页数为 10 而非 6，部分财务指标与 rubric 不一致 | PPT 结构与指标不匹配 |
| 388 | PPT 存在，但页数、日期、地点、章节、指标均与要求不符 | 产物主题和结构均错误 |
| 311 | 重跑后生成了权限 CSV，但实际列名、记录数和权限矩阵均不符合要求 | CSV schema 与权限规则错误 |

根因判断：agent 更倾向于生成“合理报告”，但没有严格按任务指定 schema 进行结构化输出。

### 4.4 明细抽取不完整

这类任务通常找到了部分正确信息，但没有穷尽所有记录，或没有按 rubric 指定粒度展开。

| Task ID | 现象 | 判断 |
| --- | --- | --- |
| 139 | 要求 60 条活动记录；实际只有约 11 条 | 记录抽取严重不完整 |
| 287 | 缺季度目标、ROI、PR4、W42 等硬指标章节 | 多源数据聚合不完整 |
| 192 | 找到了 5 份年报 PDF，但缺 R&D 增长率、五家公司核心经营表和共性风险总结 | PDF 年报抽取深度不足 |
| 337 | CSV 有基础考勤字段，但缺当月相关项目、绩效等级、规则说明等关键列 | 结构化字段覆盖不足 |
| 340 | 生日活动执行表覆盖部分阶段，但没有统一 9 列结构，预算也不匹配 | 多文档整合不完整 |
| 224 | 重跑后生成 Excel，但缺少开放平台等要求的 8 个业务线记录 | 业务线覆盖不足 |

根因判断：agent 对“全量枚举”和“精确计数”的执行较弱，尤其在任务要求包含几十条记录、多维度表格或多个源文件时容易漏项。

### 4.5 数值、实体和映射错误

这类任务产物形式可能基本正确，但核心数据与 benchmark 预期不一致。

| Task ID | 现象 | 判断 |
| --- | --- | --- |
| 23 | 库存报告缺 8 个负差异 item、6 个正差异 item 等关键统计 | 统计口径与明细错误 |
| 226 | bug report 未识别指定 Python 文件中的核心 bug | 代码审查能力不足 |
| 386 | 决策表和关系图存在，但风险、OKR 覆盖、节点结构不完整 | 会议纪要关系抽取不完整 |
| 152 | 图片文件存在，但 question mark、person、lightbulb 等图片内容与文件名错配 | 图片分类或重命名映射错误 |
| 354 | 行政计划文档存在，但关键章节、表格列、日期字段与要求不一致 | 文档结构和字段映射错误 |

根因判断：即使目标文件生成成功，agent 对细粒度实体、数值、文件名和语义标签的绑定仍不稳定。

## 5. 是否存在明显 Judge 误判

当前 clean100 口径下未发现 API 或 judge 执行异常。抽查到的低分 evidence 大多是可验证的客观检查，例如：

- 文件或目录是否存在
- 文件名是否匹配
- Excel sheet 名和列名是否匹配
- PPT 页数是否匹配
- 文本中是否包含指定关键词、数值、实体
- CSV 行数和表头是否匹配

这些 evidence 多数能直接对应候选输出文件，暂未发现大规模 judge 误判迹象。

需要人工复核的边界情况：

- 图像类任务如 `152`，部分 rubric 涉及视觉内容识别，建议人工打开图片确认是否确实错配。
- 数值口径可能存在多种解释的任务，如 `381` 的财务指标，可结合源数据人工复核 benchmark 期望。

## 6. Rubric 苛刻性与 Agent 责任边界

### 6.1 数据集的困难点

本实验中 agent 实际接收的是 `metadata.json` 里的 `task` 字段，而不是 rubrics。很多 rubrics 中的精确要求不会直接出现在 task 文本里，而是需要 agent 通过读取工作区文件自行推断。

这正是 Workspace-Bench 的难点：任务描述通常是自然语言目标，rubrics 则检查源文件中隐含的精确事实、数量、字段、命名和结构。

典型表现：

| Task ID | Task 字段中的要求 | Rubric 检查的隐藏细节 | 判断 |
| --- | --- | --- | --- |
| 139 | “生成简洁的日期-地点 itinerary” | 必须包含 60 条活动记录，并逐日抽取所有 Virtual / City 组合 | Rubric 严格，但可从源文件全量推断 |
| 224 | “按部门分类生成 Excel，汇总完成/待办/问题/后续信息” | 必须覆盖 8 个具体业务线，包括开放平台、通用平台、稳定性系统建设等 | Rubric 严格，需要深度遍历稳定性文档 |
| 337 | “结合考勤、项目进展、职责、考核标准生成核算表” | 要求 10 类列、特定岗位职责、扣分规则、绩效等级和系数 | Rubric 严格，但属于源文件可推断内容 |
| 287 | “生成季度运营执行概览并标注文档血缘” | 检查季度目标、月度硬指标、W42 周报、ROI、PR4 等具体数值 | Rubric 严格，需要多源关联和精确抽取 |
| 386 | “战略闭门会多模态数据转结构化决策表和关系图” | 检查 DEC-01~DEC-06、RISK-01~RISK-03、OKR 修订和图节点数量 | Rubric 严格，需要跨文件实体对齐 |

因此，不能简单把低分归因于 rubrics “过于苛刻”。更准确的判断是：

- rubrics 对输出结构、数量和事实准确性非常严格。
- 这些要求通常不直接写在 task 里，但可由源文件推断。
- agent 的职责是在没有 rubric 明示的情况下，完成充分的文件发现、源文件筛选、全量读取、结构化推理和最终自检。

### 6.2 Rubric 偏苛或不易从 task 推断的情况

部分 case 的 rubrics 对文件名、结构或内容有非常强的隐含期望。若 agent 只看 task 字段，确实难以直接知道最终答案的精确形态。

| Task ID | 低分原因 | 苛刻性分析 |
| --- | --- | --- |
| 288 | task 要求输出 `2015_q1_apparel_ecommerce_operations_overview_analysis_report.md`，rubric 却检查另一个更长的文件名 `2015_year_q1_apparel_ecommerce Operations Panorama competitor_product_analysis_report.md` | 文件名要求存在 task/rubric 不完全一致，属于偏苛点 |
| 381 | task 要求根据多 CSV 计算医院财务健康与疾病负担关系，rubric 检查 6 页 PPT 和特定指标数值 | 页数和章节结构没有在 task 中显式给出，需从 benchmark 预期反推，偏苛 |
| 152 | task 只要求整理并重命名图标，rubric 检查每个图标的具体视觉内容和文件名匹配 | 对非多模态模型尤其苛刻 |
| 120 | task 只说总结未命名研究截图，rubric 要求区分 AI Agent 架构、CL-Bench、开发环境三组并识别具体截图内容 | 对非多模态模型极不友好 |
| 124 | task 通过两个截图定位论文，再去 paper folder 找论文摘要 | 如果无法理解截图内容，仅凭文件名很难判断对应论文 |

这些 case 中，rubrics 并非完全无根据，但对 agent 的探索能力、多模态能力或隐含 schema 推断能力要求很高。

### 6.3 Agent 确实做得不够好的情况

更多低分 case 的失败不是 rubric 过苛，而是 agent 没有完成 task 中已经明确要求的内容。

| Task ID | 明确任务要求 | 实际问题 | 责任判断 |
| --- | --- | --- | --- |
| 7 | 创建 `project_kickoff_archive` 并复制 meeting/docs 文件 | 没有创建目标目录，输出大量扁平文件 | agent 未遵守明确路径要求 |
| 146 | 创建 `sops` 文件夹并汇总 SOP 文件 | 没有创建 `sops` 目录，文件数量也不对 | agent 未完成明确文件操作 |
| 372 | 重命名文件并移动到 `temp_pending` | 没有 `temp_pending`，只生成日志 | agent 未完成明确文件操作 |
| 131 | 创建 `backup` 子目录并备份 `.py` 文件 | 没有 `backup` 目录 | agent 未完成明确文件操作 |
| 23 | 将库存分析报告保存到 inventory optimization folder | 文件放在输出根目录，报告缺关键统计 | agent 未遵守明确路径和分析要求 |
| 226 | 调试四个 Python 文件并生成 bug report | 漏掉多个指定代码 bug | agent 代码审查不足 |
| 258 | 生成收入支出结算汇总报表 | 生成了不匹配的 sheet 结构 | agent 未按任务逻辑建模 |

这类任务即使不给 rubrics，task 字段本身也已经足够明确。失败主要是执行纪律、文件操作、结构化生成和自检不足。

### 6.4 介于两者之间的情况

还有一类任务，task 字段只描述高层目标，rubrics 检查源文件中隐含的完整事实。严格来说 rubrics 不算不合理，但 agent 必须执行非常完整的数据抽取才能通过。

| Task ID | 代表问题 | 判断 |
| --- | --- | --- |
| 139 | 只抽到约 11 条活动，而 rubric 要 60 条 | task 没写 60，但“activity planning directory”隐含需要全量遍历 |
| 287 | 缺季度目标、ROI、PR4、W42 等硬指标 | task 要“自动关联周报/月度指标/季度计划”，这些指标应从源文件抽取 |
| 337 | 缺当前项目、绩效等级、扣分规则等列 | task 明确说要结合项目进展、职责、考核标准，agent 抽取不充分 |
| 224 | 缺开放平台等业务线 | task 要“整个业务”按部门分类，agent 漏掉关键业务线 |
| 386 | 决策、风险、OKR 和图节点不完整 | task 明确要求跨文件关联，agent 完成度不足 |

这类任务体现的是 Workspace-Bench 的核心难度：rubrics 不直接暴露答案，但源文件提供了足够信息。agent 需要做完“发现、筛选、读取、归纳、验证”的闭环。

## 7. DeepSeek 非多模态能力的影响

本次 YiYi 使用 DeepSeek 文本模型作为执行模型。该模型不具备原生多模态视觉理解能力，因此对图片、截图、图标、扫描件、音频等任务有明显影响。

### 7.1 明显受影响的任务

| Task ID | 任务类型 | 影响 |
| --- | --- | --- |
| 120 | 未命名研究截图分类与总结 | 需要理解 7 张截图内容；非多模态模型只能依赖文件名、OCR 或外部脚本，容易主题识别错误 |
| 124 | 通过两张截图定位论文并抽摘要 | 关键线索在截图内容中；无法看图时很难判断截图对应 CL-BENCH 论文 |
| 152 | 科学绘图图标整理和重命名 | rubric 检查图标视觉内容与文件名匹配；非多模态模型只能用尺寸、文件名、像素脚本等弱信号，容易错配 |
| 192 | 年报 PDF 深度分析 | 若 PDF 为扫描或复杂版式，仅文本读取/抽取会漏掉表格、指标和上下文 |
| 386 | 战略会议含 `.m4a` 音频和多源材料 | 若依赖音频转写能力，文本模型只能使用已有 ASR 文本；无法直接验证音频内容 |

### 7.2 非多模态导致的典型失败方式

1. **只能读二进制文件元信息，不能理解视觉内容**

   轨迹中多次出现类似 binary file / UTF-8 读取失败的情况。对于 PNG、PPT、PDF、音频等二进制文件，如果没有可靠的解析工具或 OCR/视觉模型，agent 很难获得完整语义。

2. **用文件名、大小、路径猜测内容**

   `152` 的图标任务中，judge evidence 显示多个文件大小与预期图标不匹配，说明 agent 可能根据弱信号进行了错误映射。

3. **截图类任务容易找错主题**

   `120` 和 `124` 的核心线索来自截图内容。非多模态模型不能直接理解截图，导致截图分类错误或定位到错误论文。

4. **复杂 PDF/PPT 的结构信息损失**

   对 PDF 年报、PPT 策略报告等任务，文本抽取可能丢失表格、页结构、图形关系和版面层级，导致指标抽取不完整或页数/章节结构不符合要求。

### 7.3 可缓解但不能完全解决的方式

在不更换多模态模型的前提下，可以通过工具链缓解：

- 对 PNG/JPEG：接入 OCR、图像分类或 CLIP/视觉模型辅助识别
- 对 PDF：使用更强的 PDF parser、OCR 和表格抽取工具
- 对 PPTX：用 python-pptx 读取页数、标题、文本框和图片 alt/text
- 对音频：确保 ASR 文本存在，并在 Phase 1 明确优先使用 ASR 文件
- 对图标：用图像哈希、尺寸、主色、轮廓检测只能提供弱辅助，不能替代视觉理解

结论：DeepSeek 非多模态能力对 `120`、`124`、`152` 的影响最直接；对 `192`、`386` 等多格式任务也有间接影响，但这些任务仍可通过更强解析工具部分缓解。

## 8. 对 YiYi 执行流程的改进建议

### 8.1 强化输出路径约束

建议在 harness 或 YiYi eval prompt 中明确区分：

1. 最终产物必须保存到任务要求的相对路径
2. `model_output` 只是收集目录，不应改变任务内要求的子目录结构
3. 最终输出路径列表必须包含真实生成的目标文件，而不是中间分析文件

对目录创建类任务，应在 Phase 3 结束前进行自动校验：

- 是否存在指定目录
- 是否存在指定文件
- 文件数是否满足要求

### 8.2 增加最终产物自检步骤

在 Phase 3 后追加轻量 validator，让 agent 自检：

- 任务要求的文件名是否完全匹配
- 是否生成了要求的目录
- Excel sheet 名、CSV 表头、PPT 页数是否符合要求
- 目标记录数量是否符合要求

这类校验可以显著减少路径、文件名、sheet 名、页数等低级失败。

### 8.3 收紧检索范围和源文件选择

当前多起错误来自找错文件或主题混淆。建议：

- Phase 1 输出候选文件时，要求说明每个文件与任务关键词的对应证据
- 对论文、截图、会议纪要等任务，优先使用文件名、标题、metadata 精确匹配
- 避免把全 workspace 中“看起来相关”的文件混入目标数据源

### 8.4 对结构化产物使用代码生成与读回验证

对 Excel、CSV、PPT、PDF 等任务，建议引导 agent：

- 先生成明确 schema
- 再用 Python/openpyxl/python-pptx/reportlab 等工具生成文件
- 最后用脚本读回验证 sheet、列、页数、行数和关键值

### 8.5 强化全量抽取和计数

对于要求“全部记录”“60 条”“31 行”“19 个文件”等任务，建议增加显式计数：

- Phase 2 中列出所有源记录 ID
- Phase 3 中对输出记录数进行断言
- 输出前用脚本统计结果行数/文件数

## 9. 结论

清洗后的 100 个任务已经排除了余额不足和 judge 中断等外部异常。低分 case 的主因是任务执行质量问题，而非评测链路问题。

最核心的改进方向是：

1. 更严格地执行输出路径和文件结构要求
2. 更精确地定位源文件，避免主题混淆
3. 对结构化产物进行 schema-first 生成和读回校验
4. 对全量抽取任务增加显式计数和覆盖检查
